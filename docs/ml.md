# ML/LLM-дизайн системы

## 1. Цели ML-компонентов

ML-компоненты используются не для полного автономного управления
тикетами, а для решения отдельных задач:

- классификации темы обращения;
- оценки уверенности классификации;
- первичной маршрутизации;
- поиска релевантных материалов базы знаний;
- формирования grounded-ответа;
- сокращения ручной нагрузки операторов.

Итоговое бизнес-решение принимает отдельный Policy Engine.
Ни одна ML- или LLM-модель не должна самостоятельно разрешать
автоматическое закрытие высокорискового тикета.

## 2. Декомпозиция задач

| Подзадача | Подход | Причина выбора |
|---|---|---|
| Техническая валидация | Правила | Проверки обязательных полей и формата детерминированы |
| Базовый поиск PII | Правила и регулярные выражения | Достаточно для PoC и демонстрации архитектурной точки контроля |
| Production-поиск PII | Специализированная NER-модель + правила | Одни регулярные выражения не покрывают все формы чувствительных данных |
| Классификация темы | Классический ML | Требуются низкая задержка, предсказуемая стоимость и вероятностный output |
| Confidence | Вероятности классификатора с последующей калибровкой | Нужен сигнал для low-confidence маршрутизации |
| Risk level | Бизнес-правила | Риск определяется ценой ошибки, а не только уверенностью модели |
| Маршрутизация | Категория → команда; ML для неоднозначных случаев | Для известных категорий достаточно конфигурации |
| Поиск знаний | Лексический или гибридный retrieval | Нужно находить подтверждённые источники |
| Генерация ответа | LLM после retrieval | Ответ формируется только на основании найденного контекста |
| Итоговое действие | Policy Engine | Бизнес-правила должны быть отделены от model prediction |

## 3. Где LLM не используется

LLM не используется для:

- проверки обязательных полей;
- идентификации дубликатов;
- основной классификации каждого тикета;
- определения бизнес-риска;
- обязательной маршрутизации;
- принятия high-risk решений;
- хранения состояния;
- аудита;
- определения, можно ли автоматически закрыть тикет.

Причины:

- высокая и нестабильная latency;
- стоимость каждого вызова;
- зависимость от внешнего сервиса;
- риск недетерминированного результата;
- сложность калибровки confidence;
- риск утечки PII;
- отсутствие необходимости использовать генеративную модель
  для структурированной задачи классификации.

Основной контур классификации и маршрутизации должен продолжать
работать при полном отказе LLM.

## 4. Классификация темы

### 4.1. Первый baseline

Первый production-baseline:

```text
title + ticket text
→ TF-IDF
→ Logistic Regression
→ probabilities by category
```

Дополнительные признаки при наличии:

- канал поступления;
- язык;
- продукт или функциональность;
- длина текста;
- наличие кода ошибки;
- временные признаки;
- обезличенный пользовательский контекст.

### 4.2. Почему TF-IDF + Logistic Regression

Преимущества:

- быстрое обучение;
- низкая latency;
- отсутствие необходимости в GPU;
- интерпретируемые признаки;
- вероятностный output;
- простой deployment;
- хороший baseline для текстовой классификации;
- невысокая стоимость эксплуатации.

Ограничения:

- слабее понимает контекст и семантические перефразирования;
- зависит от качества токенизации и словаря;
- может хуже работать с короткими и неоднозначными тикетами;
- требует обработки новых терминов и категорий.

Более сложная модель принимается только при измеримом улучшении
на той же схеме валидации.

### 4.3. Возможное развитие

Следующие кандидаты:

1. Линейная модель с расширенными текстовыми и мета-признаками.
2. Предобученный text encoder.
3. Fine-tuning небольшой Transformer-модели.
4. Multi-task модель для категории и срочности.

Переход к более тяжёлой модели оправдан только при достаточном
приросте качества с учётом latency, стоимости и сложности поддержки.

## 5. Risk и confidence

### 5.1. Confidence

Confidence — оценка уверенности классификатора в выбранной категории.

Пример:

```text
category = payment_problem
confidence = 0.93
```

Confidence не гарантирует корректность и должен быть проверен
на калибровочной выборке.

### 5.2. Risk

Risk — бизнес-характеристика категории или предполагаемого действия.

Примеры высокорисковых категорий:

- платежи и возвраты;
- блокировка аккаунта;
- изменение прав доступа;
- security incident;
- юридически значимые обращения;
- операции с необратимыми последствиями.

Высокий confidence не отменяет высокий risk:

```text
confidence = 0.98
risk = high
→ HUMAN_REVIEW
```

### 5.3. Policy

Автоматический ответ разрешается только при выполнении всех условий:

```text
classification confidence >= classification threshold
AND retrieval relevance >= retrieval threshold
AND risk = low
AND PII safely processed
AND output validation passed
```

Если хотя бы одно условие не выполнено, используется:

- `DRAFT_FOR_OPERATOR`;
- `ROUTE_ONLY`;
- `HUMAN_REVIEW`.

## 6. Порог confidence

В PoC используется демонстрационный порог:

```text
classification_threshold = 0.80
```

Этот порог не считается production-настройкой.

Production-порог выбирается по validation set с учётом:

- precision и recall;
- recall высокорисковых категорий;
- стоимости ошибочного автоматического ответа;
- стоимости ручной проверки;
- допустимой нагрузки операторов;
- целевой доли автоматизации;
- калибровки модели;
- CSAT;
- reopen rate.

При снижении порога:

- растёт доля автоматизации;
- уменьшается очередь операторов;
- возрастает риск ошибочных решений.

При повышении порога:

- снижается риск автоматических ошибок;
- увеличивается ручная нагрузка;
- уменьшается экономический эффект.

## 7. PII detection

### 7.1. PoC

В PoC используется простая детерминированная реализация:

- email;
- номер телефона;
- условные идентификаторы;
- иные заранее заданные шаблоны.

Цель PoC — продемонстрировать место PII-проверки в data flow,
а не создать полноценную систему обнаружения персональных данных.

### 7.2. Production

Production-решение может комбинировать:

- регулярные выражения;
- словари;
- специализированную NER-модель;
- business rules;
- ручную проверку сложных случаев.

При невозможности безопасно удалить PII:

```text
external LLM call запрещён
→ HUMAN_REVIEW или локальная модель
```

## 8. Retrieval

### 8.1. Первый baseline

Первый retrieval-baseline:

- keyword search;
- TF-IDF similarity;
- BM25.

Причины:

- простота;
- высокая скорость;
- хорошая работа с кодами ошибок;
- хорошая работа с точными названиями продуктов;
- отсутствие необходимости в embedding service;
- лёгкая отладка.

### 8.2. Embeddings

Embeddings добавляются, если lexical retrieval недостаточно хорошо
обрабатывает перефразирования и семантически похожие запросы.

Пример:

```text
«не могу авторизоваться»
≈
«ошибка при входе в аккаунт»
```

### 8.3. Hybrid retrieval

Возможный production-вариант:

```text
BM25 candidates
+
vector search candidates
→ merge
→ reranker
→ top-k chunks
```

Лексический поиск сохраняется для:

- кодов ошибок;
- номеров документов;
- точных названий;
- редких технических терминов.

### 8.4. Retriever output

Retriever должен возвращать:

- `document_id`;
- `chunk_id`;
- текст фрагмента;
- версию документа;
- оценку релевантности;
- metadata;
- права доступа.

Если релевантность ниже порога, LLM не должна генерировать
уверенный автоматический ответ.

## 9. RAG и LLM

### 9.1. Назначение RAG

RAG используется, чтобы:

- отвечать на основании актуальной внутренней базы знаний;
- подтверждать ответ источником;
- снижать риск галлюцинаций;
- обновлять знания без переобучения LLM;
- учитывать права доступа к документам.

### 9.2. Online-путь

```text
ticket
→ retrieval
→ relevance check
→ selected knowledge chunks
→ LLM
→ output validation
→ Policy Engine
→ answer or operator
```

### 9.3. Grounded generation

LLM должна получать инструкцию:

- использовать только переданный контекст;
- не придумывать отсутствующие данные;
- явно сообщать о недостатке информации;
- формировать структурированный результат;
- не выполнять опасные действия.

RAG снижает, но не устраняет риск галлюцинаций.

### 9.4. Поведение без релевантного источника

Если источник не найден:

```text
automatic answer запрещён
→ DRAFT_FOR_OPERATOR или HUMAN_REVIEW
```

### 9.5. Поведение при отказе LLM

```text
classification and routing continue
→ automatic generation unavailable
→ ROUTE_ONLY or HUMAN_REVIEW
```

## 10. Модели и источники

### 10.1. Классификатор

Первый вариант обучается внутри компании на исторических тикетах.

Возможные дальнейшие варианты:

- готовый open-source text encoder;
- fine-tuning небольшой Transformer-модели;
- внутренний корпоративный model service.

### 10.2. Embedding-модель

Для production рассматриваются:

- открытая multilingual embedding-модель;
- внутренняя модель;
- внешний embedding API при допустимости передачи данных.

Выбор зависит от:

- качества на корпоративных текстах;
- latency;
- стоимости;
- требований к приватности;
- доступной инфраструктуры.

### 10.3. LLM

Возможные варианты:

- внешний LLM API после маскирования данных;
- локальная open-source модель;
- корпоративный LLM gateway.

Выбор зависит от:

- требований к PII;
- latency;
- качества;
- стоимости;
- доступности;
- vendor lock-in;
- возможности on-premise размещения.

В PoC используются только mock-компоненты без реальных ключей.

## 11. Данные

### 11.1. Источники данных

Для обучения и оценки могут использоваться:

- исторические тикеты;
- заголовки;
- тексты;
- каналы;
- продукты;
- финальные категории;
- фактические команды решения;
- история перенаправлений;
- ответы операторов;
- reopen;
- CSAT;
- время первого ответа;
- время решения;
- результат ручной проверки.

### 11.2. Labels

Возможные labels:

- подтверждённая тема;
- команда-владелец;
- risk level;
- срочность;
- корректность автоматического ответа;
- факт принятия черновика оператором;
- факт повторного открытия.

Исторический статус не считается автоматически правильной разметкой.

Возможные проблемы:

- ошибочная классификация оператором;
- смена справочника категорий;
- реорганизация команд;
- неоднозначные категории;
- дубликаты;
- массовые инциденты;
- устаревшие инструкции;
- неполная обратная связь.

### 11.3. Разметка

При необходимости отдельной разметки:

1. Формируется инструкция с примерами.
2. Уточняются границы категорий.
3. Часть примеров размечается несколькими экспертами.
4. Анализируются разногласия.
5. Создаётся вручную проверенный gold set.
6. Редкие и рискованные категории проверяются отдельно.

Если эксперты систематически не согласны, сначала необходимо
уточнить постановку и справочник классов, а не усложнять модель.

## 12. Подготовка выборки

Этапы:

1. Удаление технического мусора.
2. Нормализация каналов и полей.
3. Маскирование PII.
4. Дедупликация.
5. Объединение связанных тикетов.
6. Актуализация справочника категорий.
7. Удаление недоступных во время inference признаков.
8. Проверка распределения классов.
9. Отдельный анализ редких категорий.
10. Проверка качества labels.

## 13. Валидация

### 13.1. Temporal split

Используется временное разделение:

```text
train: ранний период
validation: следующий период
test: наиболее свежий период
```

Это лучше имитирует работу модели на будущих тикетах.

### 13.2. Group split

Связанные тикеты одного:

- инцидента;
- массового сбоя;
- пользователя;
- повторяющегося обращения

не должны попадать одновременно в train и test.

Иначе почти одинаковые примеры создадут leakage.

### 13.3. Leakage

Нельзя использовать как признаки:

- финальную команду;
- итоговый ответ оператора;
- время закрытия;
- reopen;
- итоговый статус;
- результат ручной проверки;
- данные, появившиеся после маршрутизации;
- будущие события пользователя.

### 13.4. Небольшой объём данных

При небольшом датасете:

- stratified cross-validation;
- оценка среднего и разброса метрик;
- bootstrap confidence intervals;
- ручной gold test set;
- error analysis;
- отдельная проверка критических сценариев.

## 14. Метрики классификации

### Основная метрика

```text
macro-F1
```

Она одинаково учитывает каждый класс и не позволяет массовым
категориям скрыть слабое качество редких классов.

### Дополнительные метрики

- precision и recall по каждому классу;
- recall высокорисковых категорий;
- confusion matrix;
- weighted-F1;
- calibration;
- Brier score или ECE;
- доля low-confidence;
- доля правильной маршрутизации;
- latency inference.

Accuracy не используется как единственная метрика из-за дисбаланса классов.

## 15. Метрики retrieval

- Recall@k;
- HitRate@k;
- MRR;
- nDCG@k;
- доля запросов без релевантного источника;
- latency;
- число переданных в LLM chunks;
- качество по категориям тикетов.

Retrieval оценивается отдельно от генерации.

Если релевантный документ не попал в top-k, LLM не сможет
надёжно сформировать grounded-ответ.

## 16. Метрики генерации

- groundedness;
- factual correctness;
- completeness;
- relevance;
- unsupported-claim rate;
- unsafe-answer rate;
- доля ответов с корректной ссылкой;
- acceptance rate оператором;
- доля ответов без ручного редактирования;
- reopen rate;
- CSAT;
- latency;
- число input/output tokens;
- стоимость ответа.

Для критических safety-метрик задаются отдельные guardrails.

## 17. Guardrail-метрики

Примеры ограничений:

```text
recall high-risk categories >= заданного порога
unsafe auto-answer rate <= допустимого значения
PII leakage incidents = 0
p95 classification latency <= 500 ms
```

Модель не допускается к автоматизации, если она улучшает общую
метрику, но нарушает safety guardrails.

## 18. Low-confidence

Low-confidence тикеты:

- не закрываются автоматически;
- отправляются оператору;
- сохраняются для последующего error analysis;
- могут использоваться для active learning.

Причины low-confidence:

- новый тип обращения;
- неоднозначный текст;
- короткий тикет;
- конфликт признаков;
- новая терминология;
- domain drift.

## 19. Active learning

Для улучшения модели приоритетно размечаются:

- low-confidence тикеты;
- частые ошибки;
- новые кластеры обращений;
- редкие high-risk категории;
- случаи разногласия модели и оператора;
- тикеты с высоким бизнес-ущербом.

Это позволяет эффективнее расходовать ресурс экспертов.

## 20. Training-serving consistency

Для снижения training-serving skew:

- используется одинаковая логика preprocessing;
- токенизация и словари версионируются;
- preprocessing сохраняется вместе с моделью;
- схема входа проверяется контрактными тестами;
- логируется версия модели и преобразований;
- production-признаки воспроизводятся на момент поступления тикета.

## 21. Версионирование

Для каждого решения сохраняются:

- версия классификатора;
- версия preprocessing;
- версия risk policy;
- пороги;
- версия retriever;
- версия embedding-модели;
- версия базы знаний;
- версия prompt;
- версия LLM.

Это позволяет воспроизводить и аудировать результат.

## 22. Rollout

Предлагаемая последовательность:

```text
offline evaluation
→ shadow mode
→ suggest-only для операторов
→ auto-answer для небольшой безопасной категории
→ canary rollout
→ постепенное расширение
```

### Shadow mode

Новая система получает копию production-трафика,
но не влияет на пользователя.

### Suggest-only

Система создаёт черновик, а оператор принимает или исправляет его.

### Auto-answer

Разрешается только для подтверждённых низкорисковых категорий
при выполнении всех quality и safety guardrails.

### Rollback

Предыдущие версии моделей, policy и prompts должны сохраняться
для быстрого возврата.

## 23. PoC-реализация

В PoC:

| Компонент | Реализация |
|---|---|
| Validator | Детерминированные проверки |
| PII detector | Регулярные выражения |
| Classifier | `MockClassifier` |
| Confidence | Фиксированный результат сценария |
| Risk | Конфигурация категорий |
| Policy Engine | Реальная доменная логика |
| Knowledge base | Небольшой JSON |
| Retrieval | Keyword или TF-IDF |
| LLM | `MockLLMClient` |
| Evaluation | Smoke-тесты сценариев |

Mock-компоненты используются не для имитации качества модели,
а для демонстрации полного data flow и архитектурных решений.

## 24. Критерии перехода от baseline

Более сложный подход принимается, если:

1. Улучшает основную метрику на фиксированном test set.
2. Не ухудшает guardrail-метрики.
3. Укладывается в требования latency.
4. Имеет приемлемую стоимость.
5. Не усложняет эксплуатацию несоразмерно эффекту.
6. Показывает стабильное качество по редким и рискованным категориям.
7. Проходит shadow и canary проверки.
