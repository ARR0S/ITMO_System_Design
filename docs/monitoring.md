# Мониторинг системы

## 1. Цели мониторинга

Мониторинг должен отвечать на пять вопросов:

1. Доступна ли система технически.
2. Укладывается ли она в требования по latency и SLA.
3. Сохраняется ли качество ML- и retrieval-компонентов.
4. Не ухудшаются ли пользовательские и бизнес-метрики.
5. Не растёт ли стоимость автоматизации быстрее создаваемого эффекта.

Мониторинг строится на нескольких уровнях:

- технические метрики;
- метрики очередей и внешних сервисов;
- метрики данных;
- ML-метрики;
- retrieval- и LLM-метрики;
- продуктовые и бизнес-метрики;
- safety-метрики;
- стоимость.

Одна группа метрик не заменяет остальные. Например, технически доступная
система может выдавать неверные ответы, а качественная модель может быть
неприемлемой из-за высокой стоимости или latency.

## 2. Наблюдаемость

Production-система должна использовать три типа сигналов:

### Metrics

Агрегированные численные показатели:

- количество запросов;
- latency;
- error rate;
- queue depth;
- model confidence;
- стоимость;
- доля human review.

### Logs

Структурированные события с контекстом:

- `ticket_id`;
- `trace_id`;
- версия модели;
- решение Policy Engine;
- причина fallback;
- ошибка внешнего сервиса;
- версия базы знаний.

### Traces

Путь одного тикета через компоненты:

```text
ingestion
→ validation
→ storage
→ classifier
→ policy
→ retrieval
→ LLM
→ audit
→ notification
```

Trace позволяет определить, в каком компоненте возникла задержка
или ошибка.

## 3. Correlation identifiers

Для каждого тикета используются:

- `ticket_id` — идентификатор бизнес-сущности;
- `request_id` — идентификатор конкретного входящего запроса;
- `trace_id` — идентификатор полного пути через компоненты;
- `task_id` — идентификатор асинхронной задачи.

Эти идентификаторы должны присутствовать в логах и audit events.

Персональные данные, полный текст тикета, пароли, токены
и незамаскированные секреты в технические логи не записываются.

## 4. Технические метрики

### 4.1. Ticket ingestion

- входящий RPS;
- число принятых тикетов;
- доля невалидных запросов;
- HTTP error rate;
- p50, p95 и p99 latency;
- доля повторных запросов;
- число предотвращённых дублей.

### 4.2. Fast path

- p50/p95/p99 времени валидации;
- p50/p95/p99 времени PII scan;
- p50/p95/p99 времени классификации;
- p50/p95/p99 времени Policy Engine;
- полная latency классификации и маршрутизации;
- error rate компонентов.

Главный технический guardrail:

```text
p95 classification and routing latency <= 500 ms
```

### 4.3. Хранилище

- latency чтения и записи;
- ошибки транзакций;
- число активных соединений;
- saturation connection pool;
- объём хранения;
- replication lag;
- доля конфликтов по `ticket_id`.

### 4.4. Workers

- число обработанных задач;
- processing time;
- success rate;
- retry rate;
- error rate;
- количество активных workers;
- utilisation workers.

## 5. Метрики очередей

Для каждой технической очереди отслеживаются:

- queue depth;
- скорость поступления задач;
- скорость обработки;
- возраст старейшей задачи;
- среднее время ожидания;
- число retries;
- число сообщений в DLQ;
- скорость роста DLQ.

Возраст старейшей задачи важнее одной длины очереди:

- большая свежая очередь может быть допустима при кратком всплеске;
- небольшая очередь со старыми задачами может означать зависший consumer.

Пример стартовых алертов:

```text
oldest message age > 5 minutes
```

```text
queue depth растёт непрерывно 10 минут
```

```text
DLQ received messages > 0 for critical workflow
```

Точные production-пороги должны уточняться после нагрузочного тестирования
и пилота.

## 6. Метрики внешней LLM

- число запросов;
- p50/p95/p99 latency;
- timeout rate;
- HTTP 429 rate;
- HTTP 5xx rate;
- retry rate;
- circuit breaker state;
- доля успешных fallback;
- число input tokens;
- число output tokens;
- стоимость одного вызова;
- стоимость одного автоматизированного тикета;
- доля тикетов, направленных в LLM.

Пример алертов:

```text
LLM timeout rate > 10% за 5 минут
```

```text
LLM p95 latency > 8 секунд за 10 минут
```

```text
circuit breaker = OPEN
```

```text
стоимость одного автоматического ответа выросла более чем на 30%
относительно недельного baseline
```

## 7. Метрики входных данных

Для текстовых тикетов отслеживаются:

- распределение длины текста;
- доля пустых и слишком коротких тикетов;
- распределение языков;
- доля неизвестных каналов;
- доля тикетов с PII;
- частота кодов ошибок;
- распределение продуктов;
- частота категорий;
- доля новых или неизвестных терминов;
- доля неуспешного preprocessing.

Эти метрики позволяют обнаружить:

- изменение каналов;
- массовый инцидент;
- новый продукт;
- изменение языка пользователей;
- поломку парсинга;
- появление нового типа тикетов.

## 8. ML-метрики классификации

Когда доступны подтверждённые labels:

- macro-F1;
- weighted-F1;
- precision и recall по категориям;
- recall высокорисковых категорий;
- confusion matrix;
- доля правильной маршрутизации;
- calibration;
- Brier score или ECE;
- качество по каналам;
- качество по языкам;
- качество по продуктам;
- качество по новым и старым категориям.

Особое внимание уделяется редким высокорисковым категориям.
Общее качество не должно скрывать падение recall критического класса.

## 9. Мгновенные proxy-метрики

Истинные labels появляются после работы оператора,
поэтому часть quality-метрик доступна с задержкой.

До получения labels отслеживаются:

- распределение confidence;
- доля low-confidence тикетов;
- доля `HUMAN_REVIEW`;
- доля `ROUTE_ONLY`;
- доля `AUTO_ANSWER`;
- доля неизвестных категорий;
- частота исправлений оператора;
- доля повторной маршрутизации;
- доля отказов retrieval;
- доля тикетов без найденного источника.

Резкий рост этих показателей является сигналом расследования,
но сам по себе не доказывает падение качества модели.

## 10. Delayed labels

Правильная категория и качество ответа могут становиться известны только после:

- подтверждения оператора;
- изменения маршрута;
- закрытия тикета;
- повторного открытия;
- пользовательской оценки;
- завершения расследования.

Мониторинг строится в два слоя:

### Online

Доступны сразу:

- latency;
- errors;
- confidence;
- prediction distribution;
- routing decisions;
- fallback rate;
- cost.

### Delayed quality

Считаются после появления labels:

- macro-F1;
- recall high-risk;
- routing accuracy;
- acceptance rate;
- reopen rate;
- CSAT;
- unsafe-answer rate.

## 11. Метрики retrieval

- Recall@k;
- HitRate@k;
- MRR;
- nDCG@k;
- доля запросов без релевантного документа;
- распределение relevance score;
- latency retrieval;
- число retrieved chunks;
- доля устаревших документов;
- качество по категориям;
- доля результатов, отфильтрованных по правам доступа.

Retrieval оценивается отдельно от LLM.

Если retrieval не находит источник, генератор не должен компенсировать
это неподтверждённым ответом.

## 12. Метрики генерации

- groundedness;
- factual correctness;
- unsupported-claim rate;
- unsafe-answer rate;
- доля ответов с корректной ссылкой;
- acceptance rate оператором;
- доля черновиков без редактирования;
- средний объём редактирования;
- refusal rate;
- latency;
- input/output tokens;
- стоимость;
- reopen rate после auto-answer;
- CSAT после auto-answer.

Часть этих метрик требует ручной или модельной оценки.
Для критичных safety-сценариев используется проверка человеком.

## 13. Safety-метрики

- число PII-инцидентов;
- доля PII, пропущенных detector;
- число high-risk тикетов, ошибочно закрытых автоматически;
- unsafe auto-answer rate;
- prompt-injection detections;
- число запрещённых tool actions;
- число ответов без подтверждённого источника;
- доля audit events с неполными полями.

Желаемый guardrail:

```text
high-risk auto-closure = 0
```

```text
known PII leakage incidents = 0
```

Эти показатели имеют более высокий приоритет,
чем рост доли автоматизации.

## 14. Продуктовые и бизнес-метрики

Основные метрики:

- время до первого ответа;
- доля SLA breach;
- среднее время решения;
- доля тикетов, закрытых без оператора;
- доля тикетов, обработанных в suggest-only режиме;
- reopen rate;
- CSAT;
- число перенаправлений;
- нагрузка на операторов;
- стоимость обработки одного тикета;
- общая стоимость поддержки;
- экономия рабочего времени операторов.

Одна из возможных North Star-метрик:

```text
доля безопасно решённых без оператора тикетов
при сохранении guardrails по CSAT, reopen rate и SLA
```

Для трека ИИ достаточно указать, какие продуктовые метрики измеряются,
даже если подробный расчёт эффекта находится вне обязательного scope.

## 15. Метрики стоимости

Отслеживаются:

- стоимость одного LLM-вызова;
- стоимость одного auto-answer;
- стоимость одного успешно решённого тикета;
- среднее число LLM-вызовов на тикет;
- input/output tokens;
- доля retries;
- доля запросов, отправленных в дорогую модель;
- стоимость embeddings и reranking;
- стоимость human review;
- экономия относительно 150 рублей за ручной тикет.

Стоимость автоматического решения оценивается вместе с качеством.

Дешёвый, но часто переоткрываемый ответ может быть дороже
корректной ручной обработки.

## 16. Data drift

Data drift означает изменение распределения входных данных:

```text
P_train(X) != P_prod(X)
```

Примеры:

- появился новый продукт;
- изменился язык обращений;
- выросла средняя длина тикета;
- появились новые коды ошибок;
- изменилось соотношение каналов;
- произошёл массовый инцидент.

Data drift не доказывает, что качество уже упало,
но повышает риск деградации.

## 17. Label drift

Label drift означает изменение долей классов:

```text
P_train(Y) != P_prod(Y)
```

Пример:

- во время сбоя категория `service_unavailable`
  начинает составлять большую часть трафика.

Это может быть временный инцидент, а не постоянное изменение системы.

## 18. Concept drift

Concept drift означает изменение связи между входом и правильным решением:

```text
P_train(Y | X) != P_prod(Y | X)
```

Примеры:

- изменились правила маршрутизации;
- обращения старой категории теперь должна обрабатывать другая команда;
- обновилась политика автоматического закрытия;
- появились новые значения риска.

В этом случае прежняя модель может ошибаться даже при похожем
распределении текстов.

## 19. Как отличать причины деградации

Диагностический порядок:

1. Проверить технические ошибки и latency.
2. Проверить состояние очередей.
3. Проверить последние deployments.
4. Проверить схему и качество входных данных.
5. Проверить preprocessing.
6. Сравнить train и production distributions.
7. Получить свежие labels.
8. Рассчитать качество по классам и сегментам.
9. Проверить изменение бизнес-правил.
10. Только после расследования решать вопрос о retraining.

Возможные ситуации:

| Наблюдение | Вероятная причина |
|---|---|
| Выросли 5xx и latency | Инфраструктурный сбой |
| Растёт очередь, workers загружены | Недостаточная processing capacity |
| Изменились тексты, labels пока нет | Data drift |
| Изменились доли категорий | Label drift или массовый инцидент |
| Вход стабилен, качество упало | Concept drift, regression или ошибка labels |
| После deployment упала одна категория | Ошибка новой модели или preprocessing |
| Offline качество высокое, online низкое | Training-serving skew |
| Качество стабильно, стоимость выросла | Prompt/token growth или больше LLM-вызовов |

Drift не является автоматическим приказом переобучить модель.

## 20. Стартовые алерты

Значения являются первоначальными и должны корректироваться по итогам пилота.

### Critical

```text
high-risk ticket auto-closed > 0
```

```text
PII leakage incident > 0
```

```text
ticket ingestion unavailable > 2 minutes
```

```text
accepted ticket lost or missing final state > 0
```

### High

```text
p95 classification and routing latency > 500 ms за 10 минут
```

```text
oldest generation task age > 5 minutes
```

```text
LLM timeout rate > 10% за 5 минут
```

```text
DLQ size растёт
```

```text
recall high-risk categories ниже согласованного guardrail
```

### Warning

```text
human review rate вырос более чем в 2 раза
```

```text
unknown category rate превышает baseline
```

```text
reopen rate auto-answer увеличился
```

```text
стоимость auto-answer выросла более чем на 30%
```

## 21. Пример расследования роста human review

Пусть доля human review выросла с 15% до 45%.

Порядок анализа:

1. Проверить, не изменился ли confidence threshold.
2. Проверить новую версию классификатора.
3. Посмотреть распределение confidence.
4. Проверить рост high-risk категорий.
5. Проверить долю неизвестных категорий.
6. Проверить, не ухудшился ли retrieval.
7. Проверить состояние LLM и fallback.
8. Разбить рост по каналам, языкам, продуктам и категориям.
9. Изучить свежую выборку тикетов вручную.
10. Проверить drift и массовый инцидент.

Нельзя автоматически снижать threshold только ради уменьшения очереди:
это может увеличить число небезопасных ответов.

## 22. Мониторинг rollout

При shadow и canary rollout сравниваются:

- latency старой и новой модели;
- error rate;
- prediction distribution;
- доля human review;
- macro-F1 после получения labels;
- recall high-risk;
- routing accuracy;
- стоимость;
- CSAT;
- reopen rate;
- safety incidents.

Условия rollback:

- нарушение safety guardrail;
- статистически или практически значимое ухудшение качества;
- рост p95 latency выше лимита;
- рост стоимости без достаточного эффекта;
- рост reopen rate;
- техническая нестабильность.

## 23. Мониторинг PoC

В PoC не разворачиваются Prometheus, Grafana и tracing platform.

Минимально реализуются:

- структурированные audit events;
- счётчики сценариев;
- логирование решений;
- счётчик вызовов LLM;
- счётчик LLM failures;
- счётчик `AUTO_ANSWER`;
- счётчик `HUMAN_REVIEW`;
- счётчик `ROUTE_ONLY`.

Пример:

```text
tickets_total
auto_answers_total
human_reviews_total
route_only_total
llm_calls_total
llm_failures_total
pii_detected_total
```

Эти счётчики подтверждают архитектурные точки мониторинга,
но не заменяют production observability stack.

## 25. Ограничения

- Некоторые ML- и бизнес-метрики доступны только после получения labels.
- Автоматическая LLM-оценка не заменяет человеческий safety review.
- Начальные алерт-пороги являются assumptions.
- Drift-метрики должны интерпретироваться вместе с продуктовым контекстом.
- Снижение одной метрики не всегда означает необходимость retraining.
